# Goal: Turn this repo into a catalogued, queryable, provenance-tracked knowledge base

## Mission

Transform this repository (`UseFullknowledge`) from an empty shell into an organized,
durable place to store and catalog knowledge produced by AI tools. The end state: any
human can browse it on the web and find what they need in seconds, any AI agent can
query it programmatically and retrieve exactly the right document, and *both* can tell
at a glance who or what created a piece of content, when, when it was last touched, and
whether it is trustworthy enough to use as context.

Assemble a team of experts to explore the design space, present the real options with
honest trade-offs, get a decision, then build the winner end to end.

## Context

- **Repo state:** greenfield. Nothing here but a two-line `README.md` and this goal file.
  There is no legacy content to migrate. You are designing from a blank slate, which
  means the conventions you pick now are the ones that will have to survive thousands of
  documents.
- **The problem being solved:** I use many different AI coding assistants and AI tools.
  They burn an enormous number of tokens producing genuinely valuable output — and that
  output currently evaporates into chat scrollback, scattered scratch files, and
  one-off directories. I want it captured once, catalogued properly, and reused instead
  of regenerated.
- **What the content actually is:** the majority is documentation explaining a
  technology, a science, or a concept, plus diagrams (C4 model diagrams especially).
  Topics vary enormously and unpredictably — today it might be Kafka partition
  rebalancing, tomorrow CRISPR base editing, next week a C4 container diagram for a
  client system. **The cataloging system must not assume a fixed subject domain.**
- **Who reads it:** humans (browsing HTML on the web) and AI agents (fetching markdown,
  grepping, or querying an index). Neither audience is secondary.
- **The trust question is the whole point.** If I cannot tell whether a document was
  written by an unverified model in one shot last November or reviewed by me last week,
  I cannot safely feed it to another AI as context. Provenance is a first-class feature,
  not metadata garnish.

## The expert team

Assemble the following roles. Run them as parallel subagents where their work is
genuinely independent, and have them critique each other's output before you synthesize.
Each expert must produce a written position, not a vague opinion.

1. **Information architect / taxonomist** — owns the organizing structure. Knows
   Diátaxis, PARA, Johnny Decimal, Zettelkasten, faceted classification, and the failure
   modes of each. Answers: how does an unpredictable topic space get shelved?
2. **Metadata & provenance governance specialist** — owns the frontmatter schema. Knows
   Dublin Core, schema.org (`CreativeWork`, `SoftwareSourceCode`), PROV-O, SPDX, and
   C2PA-style provenance thinking. Answers: what fields make trust machine-decidable?
3. **Static site / GitHub Pages engineer** — owns publishing. Knows Pages build modes
   (plain static vs. Jekyll vs. Actions-built), path and casing gotchas, `.nojekyll`,
   custom domains, and how to keep raw markdown fetchable alongside rendered HTML.
4. **AI retrieval / RAG engineer** — owns agent-facing query. Knows `llms.txt`, chunking,
   embeddings vs. lexical search, MCP servers, and — critically — when plain ripgrep over
   well-named files beats a vector store.
5. **Docs-as-code technical writer** — owns authoring ergonomics and templates. Answers:
   what does an AI agent have to do to file a document correctly, and is that cheap
   enough that it will actually happen every time?
6. **Diagram specialist (C4 / Mermaid)** — owns diagrams as first-class, versioned,
   diffable artifacts. Knows the C4 model levels, Mermaid, Structurizr DSL, and how to
   render diagrams into the published HTML without external runtime dependencies.
7. **DX / automation engineer** — owns the build script, validator, and CI. Answers: what
   runs on every commit so the repo cannot rot?
8. **Skeptic / scale adversary** — no design authority, one job: stress-test every
   proposal at **1,000 documents across 200 unrelated topics, contributed by six
   different AI tools that never talk to each other.** Where does the taxonomy collapse?
   Which convention gets silently ignored? What breaks when two agents write the same
   filename on the same day? Their objections must be answered in writing, not waved off.

## Hard requirements

These are decided. Do not re-litigate them; design within them.

### Publishing

- **GitHub Pages** is the hosting target. Public repo, static output.
- **Markdown is the source of truth. HTML is generated by a build script.** No agent
  hand-writes HTML. The pair can never drift, and provenance is copied into the HTML
  automatically.
- Raw markdown must remain directly fetchable over HTTPS (e.g.
  `raw.githubusercontent.com`) so agents can pull source without scraping rendered pages.
- The rendered site must be usable on a phone and must not depend on any paid service or
  external runtime API.

### Provenance and trust (the full trust lifecycle)

Every knowledge artifact carries frontmatter that answers, without ambiguity:

- **What created it** — tool/assistant name, model identifier, and a reference to the
  originating prompt or session where one exists.
- **When it was created** — ISO 8601 with explicit timezone offset.
- **When it was last updated** — ISO 8601 with explicit timezone offset, exact to the
  minute. If never updated, that must be unambiguous rather than blank-and-guessable.
- **Who or what updated it** — human vs. agent, and which one.
- **Review status** — a defined lifecycle (e.g. `unreviewed` → `reviewed` → `verified`),
  with the reviewer and review date recorded.
- **Confidence** — the author's honest assessment, with the basis for it.
- **Staleness** — a review-by date or explicit shelf life, so a document about a
  fast-moving library can be flagged automatically while a document about thermodynamics
  is not.
- **Sources** — citations or references where the content makes factual claims.

Additional rules:

- The **HTML output must carry the same provenance in two forms**: machine-readable
  (meta tags and/or JSON-LD) and a visible human-readable footer block on the page. A
  reader who lands on a page from a search engine must be able to judge its
  trustworthiness without opening the repo.
- The schema must be **enforced by a validator**, not by good intentions. A document with
  missing or malformed provenance fails CI.
- An agent must be able to answer "give me only `verified`, non-stale documents about X"
  using nothing but the repo contents.

### Content types (all first-class)

1. **Explanatory documents** — technology, science, and concept explainers. The bulk.
2. **Diagrams** — C4 (context/container/component/code), sequence, ER, architecture.
   Stored as source (Mermaid/DSL) plus rendered output, both provenance-tracked.
3. **Code snippets and runnable examples** — reference implementations, config samples,
   scripts. Must record what language/version they were valid for.
4. **Prompts, skills, and agent artifacts** — the reusable prompts, skills, and agent
   configs accumulated across tools.
5. **Research notes / raw AI output** — kept deliberately separate from curated docs, with
   citations, so raw material never gets mistaken for a reviewed explainer.

### Tooling

- Choose the implementation language for the build script, validator, and index
  generator yourself — but **check what is already installed on this machine first** and
  justify the choice in one paragraph. Prefer the fewest dependencies that work.

## Phase 1 — Explore the options (research and design)

Produce **at least three genuinely different candidate architectures.** Not three
variations of one idea — three designs that a reasonable person could pick between for
different reasons.

Explore explicitly along these axes, and say where each candidate lands on each:

- **Organizing structure** — strict hierarchy vs. flat namespace with tags/facets vs.
  hybrid. Consider Diátaxis (tutorial/how-to/reference/explanation), Johnny Decimal
  (numeric addressing), PARA, Zettelkasten-style linked atomic notes, and pure
  faceted classification. What happens when a document belongs in three places?
- **Index strategy** — per-directory index files vs. a single generated `catalog.json`
  manifest vs. a SQLite database committed to the repo vs. an embeddings index. What
  regenerates it, how expensive is it, and what happens when it goes out of sync?
- **Retrieval for agents** — filename/path conventions optimized for ripgrep, an
  `llms.txt` entry point, a generated catalog an agent reads first, a static search index
  (e.g. Pagefind or lunr), or an MCP server over the corpus. Which of these are worth it
  at 100 documents? At 1,000? At 10,000?
- **Retrieval for humans** — site navigation, tag browsing, full-text search, cross-links.
- **Identity and addressing** — how a document is named and referenced so links never
  break when it moves or gets renamed.
- **Contribution flow** — what a *different* AI tool has to do to add a document
  correctly without reading a manual.

For each candidate architecture, state plainly:

- How it works, with a concrete worked example: file a C4 container diagram and a
  Kafka explainer into it and show the resulting paths and frontmatter.
- **Why it would be a good choice** — the specific situations it wins in.
- **Why it would be a bad choice** — the specific situations it loses in. Every option
  must have real stated downsides; an option with no downsides means the analysis is
  incomplete.
- Cost to maintain, and what happens if maintenance lapses for six months.
- The skeptic's objections and the response to each.

Score all candidates against a stated criteria table (agent retrieval quality, human
browsability, contribution friction, resistance to topic sprawl, maintenance burden,
build complexity, link durability), then give **one clear recommendation with reasoning.**

Write this up as a comparison document in the repo.

## Decision gate — STOP HERE

**Hard stop.** Present the options and the recommendation, then wait for my decision.
Do not start building the winner, do not scaffold "just the parts common to all
options," and do not assume the recommendation is approved because it is obviously
correct. I pick, then you build.

## Phase 2 — Build the chosen architecture

Once I have chosen, implement it fully. Deliverables:

1. **Taxonomy and conventions document** — the definitive statement of how content is
   organized, named, addressed, and tagged, with worked examples.
2. **Frontmatter schema** — a machine-readable schema (JSON Schema or equivalent) for
   every content type, covering the full trust lifecycle above.
3. **Validator** — fails on missing, malformed, or internally inconsistent provenance;
   catches broken internal links; catches orphaned or unindexed documents.
4. **Build pipeline** — markdown → HTML, provenance injected into both machine-readable
   metadata and a visible page footer, diagrams rendered, output theme-aware and mobile-
   readable.
5. **Catalog / index generation** — whatever the chosen architecture requires, regenerated
   deterministically from source so it can never silently drift.
6. **GitHub Pages deployment** — a working CI workflow that validates, builds, and
   publishes on push, with a failing validation blocking the deploy.
7. **`AGENTS.md` contribution contract** — the file my *other* AI tools read so they file
   content correctly on the first try. Short, imperative, unambiguous, with a copy-paste
   template. Mirror to `CLAUDE.md` if the chosen approach warrants it.
8. **Templates** — one per content type, with frontmatter pre-filled to the point where an
   agent only has to supply what it actually knows.
9. **Three real seed documents** — one explainer, one C4 diagram, one snippet or prompt
   artifact — created through the real workflow, not hand-placed, proving the system
   works end to end.
10. **`README.md` rewrite and `llms.txt`** — the human entry point and the agent entry
    point, each pointing at the catalog.

## Verification standard

- **Nothing is reported as done without a command run and its output shown.** "The
  validator should catch that" is not evidence; run it against a deliberately broken
  document and show the failure.
- CI must be green, demonstrated, not assumed.
- Demonstrate three live queries against the finished repo:
  1. A human finding a document via the published site.
  2. An agent finding a document with no prior knowledge of the repo layout — starting
     only from the entry point file.
  3. An agent filtering to *only* trustworthy context: `verified`, reviewed within its
     shelf life, on a given topic.
- Show one deliberate negative test: a document with bad provenance must be rejected.

## Working agreement

- Parallelize the expert research; serialize the decisions.
- Check in at the decision gate and before any irreversible or repo-wide change.
- **YAGNI ruthlessly.** An elegant system nobody maintains is worth less than a plain one
  that survives. If a feature only pays off at 10,000 documents, say so and leave it out
  with a note on when to add it.
- No paid services, no databases requiring a server, no authentication, no external
  runtime APIs.
- Prefer conventions that degrade gracefully: if the build script disappears tomorrow, the
  markdown must still be readable and navigable in a plain text editor and on GitHub.

## Success criteria

- [ ] At least three architectures explored, each with stated upsides *and* downsides, scored, with one recommendation.
- [ ] I chose the architecture; the built system matches what I chose.
- [ ] Every artifact carries creator, creation timestamp, last-updated timestamp (exact, with timezone), review status, confidence, and staleness — enforced by a validator.
- [ ] HTML pages display provenance visibly and expose it machine-readably.
- [ ] Markdown and HTML cannot drift, because HTML is generated.
- [ ] Site is live on GitHub Pages; raw markdown is fetchable over HTTPS.
- [ ] All five content types have a template, a home, and a worked example.
- [ ] Another AI tool, given only `AGENTS.md`, can file a new document correctly.
- [ ] All three demonstration queries succeed, and the negative test fails as designed.

## Out of scope

- Paid services, hosted databases, vector-store SaaS, authentication, access control.
- Migrating existing content — there isn't any yet.
- Building a custom web application. This is a static site.
- Auto-generating knowledge content itself. This goal builds the shelf, not the books.
